一、修了什么：两个 P0

P0-1沙箱 async 接口是「假异步」，一条长命令冻死整个服务

位置 langchain_cubesandbox/sandbox.py 的 aexecute / aupload_files / adownload_files

根因 async def 函数体里同步直调阻塞的 e2b SDK （return self.execute(...)）。agent 是单个 uvicorn worker（单事件循环）， 于是 execute 的 timeout 上限 600s 内的任何长命令都会占死事件循环 —— 全部会话卡住、连 /healthz 都不应答 ⇒ swarm healthcheck 判 unhealthy 后 SIGKILL（task: non-zero exit (137)）⇒ 重启后又冻。

关键证据 上游 deepagents BackendProtocol.aexecute 默认实现本就是 await asyncio.to_thread(self.execute, ...)；本类覆写默认实现时 丢掉了 to_thread。且 git log -L 显示三个方法自初始 commit 8518ff3 起从未改过 —— 非本次引入。

现场吻合 11:06:54 模型决定调 execute 跑 150 页 OCR （日志「execute工具超时限制是600秒」）→ 之后无日志 → 11:10 healthcheck 累计 5 次失败 → SIGKILL。 容器内裸 TCP 连 127.0.0.1:8009 仅 3ms 成功，而同进程 GET /healthz 连续 3 次 8.008s 超时 —— 端口在听，但请求进不了事件循环。

修法 三个方法改 await asyncio.to_thread(...)，与上游对齐。 commit b9e60ea。

P0-2冷启动 4.5 分钟 > healthcheck 容忍 180s

位置 deploy/docker-compose.yml 的 healthcheck

根因 实测冷启动要 4.5 分钟 （11:00:48 容器启动 → 11:05:18 才打出 tracing 初始化日志），而旧配置容忍窗口只有 start_period 30s + retries 5 × interval 30s = 180s ⇒ 首次部署必然在就绪前 把失败计数攒满，容器一就绪就被 swarm SIGKILL。

判据差异（易混淆） 启动慢 → health 日志为 URLError: Connection refused（还没监听）； 跑起来后冻住 → 请求 timeout（端口在听但不应答）。两种死法，判据不同。

修法 start_period 30s→300s、retries 5→10 （总容忍 10 分钟）。commit 45e550b。

对照 紧接着重启的第二个容器因页缓存已热，10 秒即 healthy —— 印证差异来自冷/热页缓存，而非代码。

工具缺陷 · 已修发布验证脚本的 grep 断言曾整体静默失效

现象：三个符号断言全返 0，同时反向断言也显示 「（无命中 ✓）」—— 两个相反方向都"看起来正常"，末尾还打印 「###DONE### 未发现硬失败」。

根因 1（我的调用）：Git Bash 的 MSYS 路径转换把 --grep-file /langchain-cubesandbox/… 改写成 C:/Users/…/PortableGit/langchain-cubesandbox/…，容器里没这路径。 规避：一律加 MSYS_NO_PATHCONV=1。

根因 2（脚本自身，更严重）：grep … 2>/dev/null | wc -l 把「文件不存在」的报错吞掉，wc 恒为 0 ⇒ 判据既恒假又能假通过； 且符号 0 命中从未记入 fails。历史几次发布的符号断言可能一直在空跑。

已修：① grep 范围先独立断言存在；② 路径形如 C:/… （MSYS 痕迹）直接硬失败并提示；③ 不再吞 stderr，用 ###GREP_EXIT= 区分 无匹配(1)/出错(≥2)，出错即硬失败；④ 符号未命中记入 fails。

自证：正确调用 → ALL PASS / exit 0； 错误调用 → MISSING + 两条硬失败 / exit 1。

建议：把这条 lessons-learned 写进 AGENTS.md（需你点头，未擅自改）。

五、沉淀的判别法

客户端计时 ≠ 服务端停顿。 探针是容器内另一个进程，容器 cpus=2.0；langgraph / 模型阶段把 2 核占满会让 探针自己被 CPU 饿着 —— 客户端看到的「高延迟」混入了这个污染。 判「事件循环真停摆」还是「探针被饿着」，必须请服务端 access log 当独立证人： 按秒统计 /healthz 行数，找 >1s 的相邻空档。
别把 healthcheck 的轮询间隔误读成停摆。 docker logs 里 30s 间隔的空档，在没有探针运行时属正常 （swarm healthcheck 自己每 30s 打一次）。本轮初看有 16 处 >0.75s 空档， 逐条归因后真正的异常只有 1 处。
