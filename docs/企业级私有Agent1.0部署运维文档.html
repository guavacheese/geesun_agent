企业级私有 Agent 1.0 部署与运维文档

Digital-Factory Brain · geesun_agent 平台

版本 v1.0 · 适用环境：内网私有化部署 · 读者：IT 运维 / 接手工程师

0. 文档说明

本文档面向内部 IT 运维与新接手工程师，覆盖企业级私有 Agent 1.0（代号 Digital-Factory Brain）从 0 到 1 的部署、组件集成、日常运维与常见故障处理。平台定位为内网安全 + 业务效率的企业级私有 Agent，全部组件私有化部署，不出公网。

0.1 适用范围

  • 前端：geesun_agent_web（Next.js 16 + React 19）
  • 后端：geesun_agent（FastAPI + LangGraph + DeepAgents）
  • MCP 服务：geesun_mcp_server（FastMCP，含 DLP 解密与沙箱文件通道）
  • 沙箱底座：CubeSandbox 0.6.0（MicroVM）+ langchain-cubesandbox 桥接库
  • 模型服务：vLLM（Qwen3.6-35B-A3B）
  • 可观测：Arize Phoenix + Langfuse（OpenTelemetry 双通道）
  • 数据与目录：PostgreSQL（langgraph checkpoint）、LDAP/AD 统一认证

1. 系统架构总览

整体为五层拓扑：边缘接入 → 应用层 → 平台/AI 服务 → 沙箱底座 → 基础设施与合规。请求主链路：浏览器经 Nginx 反代访问前端（:3000），前端调用后端 API（:8009），后端编排 LLM、持久化、认证，并通过本地 MCP（:8000）完成 DLP 解密与沙箱文件通道，沙箱底座（CubeAPI :6000）拉起 MicroVM 执行代码。

1.3 调用与数据流

  • 浏览器 → Nginx(:80/443) → 前端(:3000) → 后端(:8009)
  • 后端 → vLLM(:8003) 推理；→ PostgreSQL(:5433) checkpoint；→ LDAP(:389) 认证；→ Phoenix/Langfuse(OTLP) 埋点
  • 后端 → MCP(:8000 localhost)：DLP 解密、沙箱文件上传/下载、PDF 比对 stage 编排
  • MCP → DLP 解密 API（%TSD-Header 密文解密）；→ CubeAPI(:6000) 连接 MicroVM
  • CubeAPI → MicroVM 执行代码；Harbor 供给 sandbox-code 镜像

1.4 三仓关系（关键）

后端 geesun_agent 通过 pyproject.toml 的 [tool.uv.sources] 以 editable 本地路径引入 langchain-cubesandbox，因此二者须在构建机同层目录（../langchain-cubesandbox）。geesun_agent_web 与 geesun_mcp_server 为独立仓库，分别部署。skill 目录（含 tech-spec-pdf-diff）位于 geesun_agent/skills/__user_<uid>__/ 下，由 MCP 运行时按全局搜索加载。

2. 前置依赖与环境

2.1 硬件与操作系统

  • 模型/沙箱底座：Rocky Linux 9 裸金属 @ 172.16.66.13（部署 vLLM + Cubelet 栈）
  • 开发/出网节点：OpenCloudOS 9 虚拟机 @ 192.168.10.136（4 vCPU / 7.5Gi，规划扩 16/16Gi）
  • 开发机：Windows（D:/workspace 工作区），WSL2 默认 Ubuntu 发行版

2.2 网络与证书

  • egress 192.168.10.136：clean 出网 + devpi PyPI 镜像(:3141) + cube-proxy
  • AC-gateway 172.16.66.13：SSL 中间人，需信任其伪造 CA（cube-root-ca.pem / VeriSign fake）
  • Harbor 172.16.220.74:8333：沙箱镜像源，需提前登录/pull 权限
  • 沙箱模板需带 --allow-out-cidr 192.168.10.136/32 放行 devpi 网段

2.3 账号与凭据

  • DLP ztsm 客户端（ztsmdlp.exe 等）须在本机运行，否则加密文件无法解密
  • CubeMaster 凭据（root/Geesun2020.），cube-root-ca.pem 证书
  • LDAP bind 账号（geesunai）+ base DN；JWT_SECRET 随机串

所有凭据通过 .env 注入，严禁入库（.env 已在 .gitignore）。

2.4 基础运行时与 SDK 版本要求

本平台由「Python 后端组（3 个组件）+ Node.js 前端组（1 个组件）」构成。部署前须确认目标主机已安装以下基础运行时与包管理器，且版本满足约束，否则依赖安装或前端构建会失败。

3. 逐项组件部署

3.1 CubeSandbox 0.6.0 底座

裸金属 Rocky Linux 9 @ 172.16.66.13。核心组件：CubeMaster（控制面，root/Geesun2020.）、CubeAPI(:6000)、CubeProxy（openresty 反代）、CubeEgress（MITM，证书 /etc/cube/ca/cube-root-ca.crt）、cube-lifecycle-manager（默认 5 分钟空闲 TTL）。

部署方式（任选其一，来自 CubeSandbox-0.6.0/deploy）：

  • one-click：单主机离线发布包，目标机解包后 install.sh 一键装（推荐首次）
  • kubernetes：容器编排部署
  • pvm / guest-image：裸 MicroVM 镜像或客户机镜像路线

# 单节点配置示例（configs/single-node） # cubelet.yaml / cubemaster.yaml / network-agent.yaml # NETWORK_CIDR 疑在: # /usr/local/services/cubetoolbox/Cubelet/config/config.toml # 镜像源: # sandbox-code:latest from Harbor 172.16.220.74:8333

已知注意点（部署时核对）：v1.4.9 CPU 过滤 fencepost 曾致 2 核沙箱被拒；cubemaster snapshot_reconciler 在 sandbox_list.go:132 对 GetTraceInfo 返回 nil 做 DeepCopy 会累计 panic；openresty proxy_read_timeout 默认 60s 需调到 300s 并同步 e2b SDK upload gateway timeout，否则大文件上传 504。

3.2 vLLM 模型服务

# 默认模型（OpenAI 兼容 /v1） MODEL_NAME=Qwen3.6-35B-A3B BASE_URL=http://172.16.66.13:8003/v1

  • vision 仅支持 image_url part；不支持 file type（返回 501 'Unknown part type: file'）——PDF/PPT 须走沙箱侧 pdfplumber/pdftotext 抽文本后再送
  • 可动态切换 Kimi / GLM，默认 vLLM Qwen3.6-35B-A3B（MoE 35B）

启动参数（重要，2026-08-24 实测根治 600s 超时）

  • 部署形态：systemd 裸进程 vllm-qwen3.5.service（admin 用户，Restart=always），非 docker/脚本；vLLM 0.19.0，模型 Qwen3.6-35B-A3B-FP8，--tensor-parallel-size 4。
  • 禁止加 --enforce-eager 与 --tokenizer-mode slow（过时 workaround）：eager 禁用 CUDA graph 致 decode 仅 12-14 tok/s，45k 长输入生成跑满 600s 客户端预算 → 抛 "model 调用超过 600s（vLLM 无响应或过慢）"；vLLM 侧自身无错（request_aborted=0），超时纯为引擎太慢。去掉两 flag 后 CUDA graph capture 成功（16s）、decode 恢复 ~185-202 tok/s（约 15× 提升），长请求正常完成。
  • 正确 ExecStart（CLEAN 基线，备份 /tmp/vllm-clean.service）：vllm serve /home/admin/vllm_models/Qwen/Qwen3.6-35B-A3B-FP8 --served-model-name Qwen3.6-35B-A3B --tensor-parallel-size 4 --port 8003 --api-key <占位符> --gpu-memory-utilization 0.9 --trust-remote-code --enable-auto-tool-choice --tool-call-parser qwen3_xml。
  • 验证：重启后 journalctl -u vllm-qwen3.5.service 应见 "Graph capturing finished in 16 secs"；长请求期间 Avg generation throughput（纯 decode 窗口）≥ 100 tok/s、无 ERROR/abort。

3.3 PostgreSQL

POSTGRES_HOST=192.168.10.136 POSTGRES_PORT=5433 POSTGRES_DB=agent_mem POSTGRES_USER=geesun POSTGRES_PASSWORD=<占位符，向 IT 索取>

承载 langgraph checkpoint（postgres / sqlite 双后端支持）。建议每日逻辑备份 + WAL 归档；升级前先 pg_dump agent_mem。

连接池（重要，2026-08-24 实测根治"会话刷新丢消息/丢任务"）

  • langgraph AsyncPostgresStore/AsyncPostgresSaver 的 from_conn_string 默认创建单条共享 AsyncConnection（非连接池）。并发时（流式任务写 checkpoint + 断连兜底 aget_state + 刷新 GET /messages 读 + list_sessions 读）同一连接被两个协程抢用 → psycopg 抛 another command is already in progress（server.log 实锤）→ 读失败被吞 → 已完成的会话"刷新空白"；断连兜底 _persist_session 写失败被吞 → 进行中任务的消息从未落库（真丢）。
  • 已修复（commit 2bbd075）：store 端 from_conn_string 传 pool_config={"max_size": 20}；saver 端 from_conn_string 不支持 pool，手动 AsyncConnectionPool(dsn, min_size=1, max_size=20, open=False, kwargs={"autocommit": True, "prepare_threshold": 0, "row_factory": dict_row}) + await pool.open() 后 AsyncPostgresSaver(conn=pool, serde=None)。两端 _reconnect/aclose 关闭连接池（勿把 _reconnect 写成永久 pool.close()）。
  • 注意：saver 自带实例锁 asyncio.Lock（langgraph 已知行为），其操作仍串行化——连接池解决的是"连接级并发碰撞"（本次丢数据根因），不等同于 saver 全并行。
  • 并发量可调：POSTGRES_POOL_MAX_SIZE（默认 20），按在线会话数调整。

3.6 geesun_mcp_server

FastMCP 服务，监听 127.0.0.1:8000（streamable-http），与后端同机 localhost 部署。

关键工具：

  • copy_script_to_sandbox / upload_to_sandbox / download_from_sandbox：沙箱文件通道
  • run_pdf_diff_stage1 / run_pdf_diff_stage3：技术协议 PDF 比对确定性流程

环境变量：

DECRYPT_API_URL=<DLP 解密 API 地址> E2B_API_URL=<CubeAPI 地址，同 CUBE_API_URL> E2B_API_KEY=<占位符> SSL_CERT_FILE=<cube-root-ca.pem 路径> AGENT_WORKSPACE=<同后端> UPLOAD_ROOT=<同后端> REPORT_ROOT=<同后端>

3.7 geesun_agent_web 前端

Next.js 16.2.9 + React 19.2.4 + Tailwind + shadcn + @base-ui，Turbopack 构建，使用 bun。

# package.json scripts "dev": "next dev" "build": "next build" "start": "next start" # .env.local NEXT_PUBLIC_API_BASE=http://localhost:8009

生产：next build && next start（默认 :3000），前置 Nginx 反代 :80/:443 到 :3000。注意：WSL 内启动的 dev server 与 Windows 侧 localhost 不通，验证需在 WSL 内或浏览器。

3.8 Arize Phoenix + Langfuse

双通道链路追踪并行采集：

  • Phoenix：OTLP gRPC，由 PHOENIX_COLLECTOR_ENDPOINT 指定 collector 地址
  • Langfuse：OTLP HTTP ingest，由 LANGFUSE_SECRET_KEY/PUBLIC_KEY/BASE_URL 配置
  • openinference-instrumentation-langchain 自动埋点 LangChain/LangGraph，用于调试、评估与回归分析

部署形态：可本地进程或独立服务端；建议独立服务以便长期留存 trace。

4. 集成与联调

4.1 端到端冒烟测试

典型链路：上传加密 PDF → 前端 → 后端 → MCP upload_to_sandbox（自动检测 %TSD-Header 解密写沙箱，明文不落盘；decrypt_and_upload_to_sandbox 为等价显式入口）→ 沙箱内跑 skill 脚本（extract → diff → generate）→ download_from_sandbox 拉回报告。

# 关键校验点 # 1) 加密文件上传用 upload_to_sandbox 即可（已内置 DLP 兜底：检测到 %TSD-Header 自动解密上传；decrypt_and_upload_to_sandbox 等价仍可用） # 2) 沙箱内 pdfplumber 缺失时 stage1 自动 pip install（离线需配 devpi 镜像） # 3) 扫描件/图片型 PDF（平均页字符 < 50）会明确报错，不静默出空报告

4.2 会话与状态

  • SSE 会话隔离：切换会话存在 race condition 致内容串流的已知 Bug，须使用已修复版本
  • __index__ 索引：更新已有 session 须维护索引，否则 GET /sessions 返回空列表（历史 Bug）
  • 沙箱生命周期：业务沙箱由 Agent 管理，GC 不得 kill 业务沙箱（GC-kill 链曾致反复 504）

5. 安全与合规

  • DLP 不落盘：解密明文走 decrypt MCP 内存 base64，绝不 open(orig,'wb') 直写；0x80 为完整加密标志、0x00 为半加密态
  • AC-gateway MITM：出网 HTTPS 经伪造 CA，客户端须信任 cube-root-ca.pem
  • egress 管控：仅放行白名单网段；沙箱内 pip 走 devpi 镜像 192.168.10.136:3141
  • JWT：JWT_SECRET 用随机串，有效期 168h；最小权限原则
  • .env 不入库；凭据分级管理，禁止提交明文

6. 运维手册

6.1 启停

  • 后端：./start.sh（uv run uvicorn :8009）或 systemd 托管
  • 前端：next build && next start（:3000），Nginx 反代
  • MCP：与后端同机 uv run 启动（:8000）
  • CubeSandbox：systemd 托管 CubeMaster / CubeAPI / CubeProxy / lifecycle-manager

7. 常见故障 FAQ

Q：上传加密 PDF 报"检测到 DLP 加密文件"

A：说明文件是密文。用 upload_to_sandbox 上传即可（工具会自动检测 %TSD-Header 并解密上传，明文不落盘）；decrypt_and_upload_to_sandbox 为等价显式入口。

Q：沙箱跑脚本报 pdfplumber 缺失

A：stage1 会自动 pip install pdfplumber；若离线/超时，需在沙箱模板配置 devpi 镜像 192.168.10.136:3141 或预装。

Q：模型返回 501 Unknown part type: file

A：Qwen API 不支持 file-type content。PDF/PPT 不能直传，须走沙箱侧 pdfplumber/pdftotext 抽文本再送模型。

Q：SSE 串会话 / GET /sessions 返回空

A：历史 race condition（切换会话内容串流）与 __index__ 索引未维护导致。升级到已修复版本，并确认 session 索引在更新时维护。

Q：沙箱调用反复 504

A：可能来自 GC-kill 链（沙箱对象 GC 时被 kill）或 openresty proxy_read_timeout 默认 60s 过短。将 proxy_read_timeout 调到 300s 并同步 e2b SDK upload gateway timeout。

Q：前端改完代码无变化

A：Turbopack 偶发 .next/dev/types/routes.d.ts 缓存失效。删 .next 目录后重启 dev server。

Q：解密后仍是明文 PK 未触发 0x80 完整加密

A：DLP 策略可能只产出半加密(0x00)。若需完整加密，用 Office 打开后"另存为"同路径，Office 保存会触发 DLP 完整加密(0x80)。

Q：沙箱内 pip 安装慢/超时

A：沙箱内统一走 devpi 镜像 192.168.10.136:3141（模板需 --allow-out-cidr 放行该网段），不要预打包全部依赖。
