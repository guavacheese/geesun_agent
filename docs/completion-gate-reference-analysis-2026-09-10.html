完成门 / 空响应 / 交付物校验：deer-flow 与 deepseek-harness 对照分析

承接 2026-09-10 生产事故：会话 GY24428:0f6d781d 因模型返回空响应 + auto_continue=false， 被 M3 完成门判为「本轮未产出交付物」终局失败。
本文回答三问：它们有没有做这种门？怎么做的？我们能否借鉴、代码兼容吗？
分析对象：D:\github\deer-flow（backend/packages/harness）· D:\github\deepseek-harness（packages/llm）
三句话结论：
  1. 两者都做了，而且都比我们成熟——但路径完全不同。 deer-flow 在 Agent 中间件层补一个「终点响应守卫」；deepseek-harness 在 适配器层把空响应直接定义成 EMPTY_RESPONSE 错误码 + 有界退避重试。
  2. 我们的 bug，deer-flow 有 1:1 的现成解（TerminalResponseMiddleware）， 且我们已经移植过它的姊妹中间件（LoopDetectionMiddleware，agent.py:836 注释确认）， 部署版本也用同一套 langchain 1.3.13 中间件 API。兼容性已逐项实测验证。
  3. 但两者各有一个盲区，且都落在我们这次的故障点上——照抄任何一个都不够， 需要用「互补组合」+ 补一个我们独有的 reasoning 感知空判定。

一、deer-flow：Agent 中间件层的「终点响应守卫」

D:\github\deer-flow\backend\packages\harness\deerflow\agents\middlewares\

deer-flow 的核心不是「完成门」（校验交付物），而是「防静默成功」—— 它不去检查 /reports 是否为空，而是守住对话是否以一条空的 assistant 消息结束。 这个定位差异非常关键，后面会展开。

1.1 TerminalResponseMiddleware — 与我们的 bug 一一对应

terminal_response_middleware.py（224 行）

它的自述就写明了要防的场景，与我们遇到的完全一致：

"""Retry one empty post-tool response, then persist a visible error fallback."""

_RECOVERY_PROMPT = (
    "<system_reminder>\n"
    "Your previous response after the tool execution was empty. Review the tool results "
    "already present in the conversation and provide a concise, user-visible final response. "
    "Do not call another tool unless it is strictly necessary.\n"
    "</system_reminder>"
)
_FALLBACK_CONTENT = "The model completed the tool run but returned no final response, "
                    "including after one automatic retry. Please try again or use a different model."

触发条件（三个 AND，非常克制）

if _has_visible_content(last) or _has_tool_call_intent_or_error(last):
    return None                      # 有正文或有工具意图 → 不管
if not _tool_result_in_current_turn(messages):
    return None                      # 本轮没有工具结果 → 不管

要点_tool_result_in_current_turn 以最后一条真实 HumanMessage为界， 只在本轮真的跑过工具时才守——避免把「用户刚发消息、模型还没回」的正常中间态误判。非常严谨。

两步处置：先重试一次，再落可读降级文案

# 第 1 次命中：删掉空消息 + 跳回 model 重跑（不是抛错、不是判失败）
if retry_count == 0:
    message_updates = [RemoveMessage(id=last.id)] if last.id else []
    return {"messages": message_updates, "jump_to": "model"}

# 第 2 次仍空：写一条用户可见的降级文案，绝不留空
fallback = last.model_copy(update={"content": _FALLBACK_CONTENT, ...})

重试提示的注入方式 — 这是最值得抄的一手

def _augment_request(self, request: ModelRequest) -> ModelRequest:
    ... if pending:
    reminder = HumanMessage(
        content=_RECOVERY_PROMPT,
        name="terminal_response_recovery",
        additional_kwargs={"hide_from_ui": True},   # 用户看不到这条
    )
    return request.override(messages=[*request.messages, reminder])

要点用 HumanMessage + hide_from_ui 而非 SystemMessage。 这一手同时解决我们的两个历史痛点： ① 我们 chat.py:1379 用的 SystemMessage 曾触发 vLLM 400 「System message must be at the beginning」（chat.py:1264-1267 有记载）； ② 恢复提示会污染 UI 对话流。

重试预算作用域 = 每次 run（不是每条空消息）

# The recovery budget is once per run, not once per empty message.
# A retry that calls another tool must not refresh the budget and
# create an unbounded empty -> retry -> tool loop.
self._retry_counts: BoundedDict[tuple[str, str], int] = BoundedDict(1000)

key = (thread_id, run_id)，并在 before_agent / after_agent 清理。 这是防止「空 → 重试 → 调工具 → 又空」死循环的关键，我们的 auto_continue 预算没有这层防护。

1.2 它其实有三层「终止原因」处理，但彼此有缝

中间件触发条件动作对空响应的覆盖
TerminalResponseMiddleware
terminal_response_middleware.py		 最后一条 AI 消息空正文且无工具调用，且本轮有工具结果 重试 1 次 → 仍空则写降级文案 完整覆盖
ModelLengthFinishReasonMiddleware
model_length_finish_reason_middleware.py		 finish_reason='length' 且有可见正文、无工具意图 只打标 stop_reason='model_length_capped'，不改内容 明确排除空内容

SafetyFinishReasonMiddleware
safety_finish_reason_middleware.py		 provider 安全终止信号（content_filter/refusal/SAFETY） 且（有工具调用 或 内容空白） 剥离截断的 tool_calls；内容空则回填解释文案 覆盖空内容，但仅限安全终止
它的 issue #4393 正是「空响应毒化会话」
发现的盲区 1（deer-flow 侧）：finish_reason='length' + 内容为空，三个中间件都不覆盖。
  • TerminalResponseMiddleware 会兜住它（因为它是「空 + 无工具调用」），但只重试一次， 且恢复提示写的是「Your previous response ... was empty」——没有告诉模型「你的输出预算被截断了」。
  • 对「thinking 吃光 max_tokens」这种情形，模型下次很可能又思考到截断，一次重试不足以恢复。
  • ModelLengthFinishReasonMiddleware 本可以给出精准信号，但它的守卫把「无可见正文」直接排除， 于是最常见的截断形态（截在思考段内）反而没有 model_length_capped 标记。
另一个发现（属我的代码推断，非实测，需谨慎）：SafetyFinishReasonMiddleware 可能根本没被触发。
它的 docstring 自陈依赖「LangChain factory 按逆序接 after_model 边， 最后注册的中间件最先看到模型输出」，并据此要求在 LoopDetectionMiddleware 之后注册。
但 lead_agent/agent.py:667-673 注释说的是另一套： 「Registered after the terminal-response ... so LangChain's reverse-order after_model dispatch runs Safety first」—— 作者认为后注册 = 先执行。而该中间件自己的 docstring 说「the last registered middleware is the first to observe」—— 两处描述自相矛盾（逆序 vs 正序）。
若实际是正序或存在 pending 状态残留，则该中间件会「注册了但永不触发」， 其作者在 from_config 里特意拒绝空 detector 列表、称其为 「the worst of both worlds」就是这个担忧。这一条我未运行验证，仅作为「照抄时需实测」的风险提示。

1.3 交付物校验：产出「结构化 receipt」，而不是一句布尔失败

runtime/runs/worker.py:187-221 · workspace_changes/scanner.py

deer-flow 确实也做交付物校验（对应我们的 M3），但它的产出是一个状态机式的 receipt：

def _delivery_content_with_outputs(content, produced_paths):
    presented_paths = content.get("by_tool", {}).get("present_files", [])
    matched_paths = [p for p in produced_paths
                     if any(_presented_path_covers_output(pp, p) for pp in presented_paths)]
    satisfied = bool(matched_paths)
    return {
        **content,
        "verification": {"source": "outputs_changed",
                         "requirement": "present_files_matches_produced_output"},
        "produced_paths": produced_paths,
        "presented_paths": presented_paths,
        "matched_paths": matched_paths,
        "stage": "presented" if satisfied else ("mismatched" if presented_paths else "not_started"),
        "satisfied": satisfied,
    }

可借鉴把「失败」拆成 not_started（压根没产出） / mismatched（产出了但没呈现）/ presented（合规）三态。 我们目前只有布尔 completion="blocked_no_output"， 把「模型没回答」和「模型回答了但忘了 download」混成同一个文案—— 这正是用户抱怨「不友好」的技术根源。

另外它的交付判定基于工作区快照 diff（workspace_changes/scanner.py）， 带完整的目录排除表（.git/.venv/.tool-results/browser-frames 等）， 并且明确注释了排除理由——比我们的 snapshot_report_files 差集更系统。

二、deepseek-harness：适配器层的「空响应 = 可重试错误」

D:\github\deepseek-harness\packages\llm\

deepseek-harness 的思路更靠底层、更彻底：它不在 Agent 层打补丁， 而是在 provider 适配器把空响应归类为协议错误，让它走既有的重试通道。

2.1 核心决策：空响应不是「成功的空消息」，而是「错误 finish」

packages/llm/llm/README.md:85 · llm-deepseek/src/translate.ts:110-116
const reason = pendingFinish ?? { kind: 'stop' as const }
yield {
  type: 'finish',
  reason: reason.kind === 'stop' && order.length === 0
    ? {
        kind: 'error',
        failure: { message: 'model returned a completed response with no content',
                   code: EMPTY_RESPONSE_CODE },
      }
    : reason,
}

README 的原话（中文版同样明确）：

EMPTY_RESPONSE_CODE — 两个适配器都使用的提供方无关 code，用于表示退化的提供方生成结果：
一个未携带任何内容块的终止 stop。它会被分类为错误 finish（而非成功空消息），
因为尝试未产生持久内容；dsh-llm-retry 默认重试它。

设计要点判定条件是 order.length === 0——即 一个内容块都没打开。注意 order 同时收纳 text、reasoning、 tool 三类块，所以「只有 reasoning、没有正文」不会被判为空响应 （这也正是它的盲区，见 2.3）。

2.2 重试是「一等公民」：有界指数退避 + 抖动，默认 5 次

packages/llm/llm/src/retry-policy.ts:13-23
const DEFAULT_MAX_RETRIES = 5
const DEFAULT_INITIAL_DELAY_MS = 500
const DEFAULT_MAX_DELAY_MS = 10_000
const DEFAULT_JITTER_RATIO = 0.1
const DEFAULT_RETRYABLE_CODES = Object.freeze([
  EMPTY_RESPONSE_CODE,   # ← 空响应排在第一个
  'RATE_LIMIT', 'SERVER', 'TIMEOUT', 'TRANSPORT',
])

它把「临时性失败」收敛成一个极小的、可配置的 code 集合， 并明确写出「加一个 code 需要适配器 fixture + 有记录的策略决策」。工程纪律很强。

几处设计细节值得我们直接学

机制做法对我们的价值
重试预算归属 重试策略插件挂在 agent/request-error 扩展点，不新增 loop 分支； 连续失败历史由 loop 拥有，成功后清空 我们若加重试，应避免在 chat.py 的 while 循环里再堆分支

2.3 它的盲区：reasoning 块会掩盖「思考截断」

deepseek-harness 判定空响应用的是 order.length === 0（任何内容块都没开）。 但 reasoning 是独立块，会被计入 order。于是：

模型思考了 6 万 token、被 max_tokens 截断、正文一个字没出
→ 已开 reasoning 块 → order.length > 0 → 不判 EMPTY_RESPONSE
→ 不重试 → 作为「成功的空正文消息」结束

盲区它防住了「完全没吐任何东西」，但防不住 「只吐了思考、正文被截断」——而这恰好是我们本次故障的首要假设 （336s ≈ 65536 tokens ≈ model_max_tokens，且 stream_chunk_timeout=240s 未触发， 反证模型确实在持续吐字）。

由此得出本次分析最有价值的一条结论：
deer-flow 的空判定是 content_is_blank = not message_content_to_text(last.content).strip() ——会把「只思考无正文」判为空（因为 reasoning 存在 additional_kwargs，不在 content 里）， 但它的重试提示不提截断，且只重试 1 次；
deepseek-harness 的重试机制更强（5 次 + 退避 + 可见事件），但它的空判定看不见「思考截断」。
两者的盲区正好互补，而我们的场景同时踩中了两边。 因此正确做法不是二选一，而是：deer-flow 的判定位置 + deepseek-harness 的重试强度 + 我们自研的截断识别。

4.2 需要改动的接入点（两处，都很小）

差异 1：我们没传 context=，deer-flow 的中间件依赖 runtime.context

# 我们现在的调用（chat.py:342、762）

# deer-flow 依赖的（terminal_response_middleware.py:93-98）

    if isinstance(context, dict):
        thread_id = str(context.get("thread_id") ...)

影响：runtime.context 在我们这儿为 None， deer-flow 有防御性 fallback（("unknown-thread", str(id(runtime)))）， 所以不会崩，但 per-run 预算会退化成 per-runtime-object，等价性下降。

两个选项：推荐改用 langgraph.config.get_config() 读 configurable.thread_id（零调用方改动，config.py:17 已确认可用）； 或给 astream 加 context={"thread_id": ...}（需改 2 处调用点）。

差异 2：我们的 reasoning_content 存在 additional_kwargs，不在 content 里

# 我们的 ReasoningChatOpenAI 写入位置（model.py:299、333）
msg.additional_kwargs["reasoning_content"] = rc

好消息：这意味着 deer-flow 的 content_is_blank 判定天然正确—— 「只思考无正文」时 content 确实为空、additional_kwargs 里有思考文本， 两者分离，正好可以据此做更精细的判定：

if 无 content 且 无 tool_calls:

        → "思考截断"：提高重试提示的针对性（提示收敛/直接输出），

    else:
        → "完全空响应"：按 EMPTY_RESPONSE 语义重试

这个三分支判定是两个参考项目都没有的，但我们的数据结构支持它——是我们的信息优势。

  • 不引入 BoundedDict(1000) 这种内存态预算——我们单实例部署， 用 get_config() 读 thread_id + 一个轻量 dict 即可，无需引入有界容器。

六、关键差异提醒：我们的 M3 比 deer-flow 的 delivery 更严

deer-flow 的 delivery 校验只在「本轮真的产出了 output 但没 present」时失败 （_delivery_error 先判 if not content.get("produced_paths"): return None）； 而我们把「零产出」本身判成失败并对交付类任务强制拦截。

这是个有意的强化（用户要求交付物就必须有交付物），本身合理； 但代价就是必须配套一个「模型确实回答了」的守卫，否则模型侧任何异常 都会以「你没交作业」的口吻呈现给用户。

所以 A（终点响应守卫）不是可选优化，而是 C 与现有 M3 能否自洽的前提。

七、说人话：那四个名词分别是什么

先给一个统一心智模型：deer-flow 把「一轮对话的收尾」拆成了四道哨卡，每道只管一件事， 互不越权。下面逐个翻译成人话。

7.1 TerminalResponseMiddleware —— 「话说到一半突然闭嘴」的兜底

它解决的问题：模型调了一堆工具、工具也都跑完了，轮到它说最后一句总结的时候， 它吐了一个空白（content 空、也没有 tool_calls）。前端就显示一片空白，用户一脸懵。

它的做法（两步，且只重试一次）：
  1. 第一次发现空白：把这条空白消息删掉（RemoveMessage，免得它留在历史里污染后续上下文）， 然后把球踢回给模型（jump_to="model"），同时偷偷塞一句话进去： 「你上一轮工具跑完之后没说话，请根据已有工具结果给个简洁的最终答复，别再调工具了。」 —— 这句话用 HumanMessage + hide_from_ui: True 包装，用户看不见。
  2. 第二次还是空白：认输，把这条消息的 content 改写成一句人话： 「模型跑完了工具但没给最终回复（自动重试一次也没用），请重试或换个模型。」 并在 additional_kwargs 里打标记 deerflow_error_fallback: True 方便排查。
关键设计（也是它比我们成熟的地方）：重试预算是 「每次 run 只给 1 次」，不是「每条空消息给 1 次」。 代码注释写得很直白——"A retry that calls another tool must not refresh the budget and create an unbounded empty -> retry -> tool loop"， 防止模型陷入「空 → 重试 → 调工具 → 又空 → 再重试」的无限循环。

三个前置判定（不是所有空响应都该触发）： _has_visible_content()（真的没可见正文）+ _has_tool_call_intent_or_error()（也没有 tool_call 意图或畸形调用）+ _tool_result_in_current_turn()（本轮确实有过工具结果——否则这是另一种失败，不该由它管）。

7.2 ModelLengthFinishReasonMiddleware —— 「不是模型不想说，是它被掐断了」

它解决的问题：模型其实说了一半正常内容，但输出预算用完了，被硬生生截断 （provider 用 finish_reason='length' 告诉你）。这时候如果什么都不做， 系统会当成「正常结束」，用户拿到半截答案还以为说完了——这是最危险的一种静默失败。

它的做法：不打补丁、不改内容、不假装能修复，只是盖一个章： 在运行上下文里写 stop_reason = 'model_length_capped'， 让上层（日志、trace、UI）知道「这次是被长度掐断的」。

它的自我克制（划重点）：只在「有可见内容 + 被标记 length」时才盖章。 代码里明确写着 if not _has_visible_content(last): return None —— 空 content 它不管，因为那种情况归 7.1 管、或者归安全类问题管。 这种「各管一段、绝不越界」的边界感，正是它这套东西好维护的原因。

7.3 SafetyFinishReasonMiddleware —— 「模型被安全策略当场捂嘴」

它解决的问题（两个，都很脏）：
  • #3028 半截的 tool_call 被当真执行了：模型正要 write_file，写到一半被安全策略掐断， 参数是残的（比如 markdown 正文断在半句话中间）。但 LangChain 的工具路由只要看到 tool_calls 非空就认为「去执行吧」→ 于是残缺文件被真的写进了磁盘， 模型看到写残了的文件又想修，修的时候又被过滤……死循环。
  • #4393 空响应污染整个 thread：模型被安全终止后留下一条空的 assistant 消息。 之后每次请求，严格的 OpenAI 兼容 provider 都会报 "message ... with role 'assistant' must not be empty" —— 这个会话就废了，用户只能新开一个聊天。
它的做法：在 after_model 拦下来，分两种情况处理——
  • 如果是带 tool_call 的截断：把 tool_call 连根拔掉（结构化的和 provider 原始 payload 都清）， 防止残参被执行；
  • 如果是完全空白：塞一句面向用户的解释进去，别让空消息落盘；
  • 如果有正文但没 tool_call：原样放行——半截答案也比没有强，让用户自己判断。
并把处置详情塞进 additional_kwargs.safety_termination 供日志/trace/SSE 消费。

它的注册位置有讲究：docstring 明说要注册在 LoopDetectionMiddleware 之后， 因为「最后注册的中间件最先看到模型输出」→ Safety 先拿到原始响应、先清 tool_call， Loop 再基于清理后的消息做计数，顺序反了就会算错。

7.4 结构化交付回执 —— 「到底交没交作业，别靠嘴上说」

这个和上面三个不是一层的东西：上面三个是拦截器，这个是一次性运行的结案报告。 代码在 runtime/runs/worker.py:183-221 的 _delivery_content_with_outputs()。
它解决的问题：agent 说「我做好了」并不等于真的产出了文件，更不等于用户真的拿到了文件。 需要一个客观核对，而且要能区分「没做」「做了但没交付」「交付了」三种情况。

它的做法：一次 run 结束后，比对本轮实际改动的工作区文件（produced_paths） 和 agent 声称交付给用户的文件（presented_paths，来自 present_files 工具调用记录），算出交集 matched_paths， 然后给一个三元 stage：
stage含义人话
not_startedproduced_paths 有，但 presented_paths 空 做了但压根没交——文件躺在工作区，用户没拿到（我们这次就是这个情况的极端版：连 produced 都没有）
mismatched两边都有，但没有一个对得上 交错了东西——交付的文件不在本轮产出里（可能是旧文件，或路径写错）
presented至少有一个产出路径被交付覆盖 正常交作业，satisfied = true
配套还有一个 satisfied: bool 布尔位和 verification.source = "outputs_changed" 用来声明「我这个判定是基于工作区 diff 算出来的」，可追溯、可质疑。

它还顺手修了一个容易踩的坑：workspace_changes/scanner.py 里有个 EXCLUDED_DIR_NAMES，把 .tool-results（工具输出超长时外置的暂存目录）、 .git、.venv、browser-frames 等排除在「交付物」之外。 否则 agent 随手读了几个大文件、系统把工具输出落盘到 .tool-results， 就会被误判成「产出了交付物」。

为什么说这个对我们最关键：我们现在的 M3 只有「/reports 有没有文件」这个二元判断， 所以当模型一个 tool_call 都没发出时，我们只能说「你没交作业」， 然后把责任推给模型（「请检查是否遗漏 download_from_sandbox / write_file 步骤」）。 deer-flow 这套东西的价值就在于把「没交作业」拆成了三种不同原因， 每种原因对应不同的处置和不同的话术——这才是它比我们成熟的核心。

八、中间件顺序契约：已实测裁决（原第七章第 1 条）

结论：deer-flow 的 docstring 是对的，after_model 逆序执行——最后注册的最先看到模型输出。
不再是「两种说法矛盾、需实测」，已用两轮 spike 在 langchain 1.3.13 上跑实。 但实测同时挖出了两个 deer-flow 没说、我们也必须处理的问题（见 8.3 / 8.4）。

8.2 这条结论对我们的直接指导

我们 agent.py:822-842 的注册顺序是 [_FreshSkillsMiddleware, switch_model, file_to_image, summarization_mw, model_call_guard, LoopDetectionMiddleware]， 上游 deepagents 还会在我们之前追加 base stack，在我们之后追加 tail stack。 按逆序规则，真正最先看到模型输出的是「最后注册的那个」。把整条链按「观察顺序」展开：
观察顺序中间件有无 after_model对空响应的影响
1HumanInTheLoopMiddleware（tail 最末）有 human_in_the_loop.py:405 首个判断就是 if not last_ai_msg or not last_ai_msg.tool_calls: return None → 空响应它直接放行，不干扰
2MemoryMiddleware / prompt-caching / _ToolExclusionMiddleware无不影响
3我们的 LoopDetectionMiddleware有 只做重复计数 + 硬剥 tool_calls；空响应无 tool_calls 可剥，不会改消息
4我们的 model_call_guard / summarization_mw / file_to_image / switch_model无不影响
5_FreshSkillsMiddleware（我们最前 = 最后观察）无（只有 before_agent）不影响
6deepagents base stack（PatchToolCalls / Summarization / SubAgent / Filesystem / Skills） 仅 TodoListMiddleware 有依据 agent.py:836 已实现「只补不改」，需 spike 复核（见 8.5）
推论：如果我们把 A（TerminalResponseMiddleware）追加在 agent.py middleware 列表的最后 （即 LoopDetectionMiddleware 之后），它会在 HumanInTheLoop 之后、LoopDetection 之前拿到输出。 这个位置是安全的：HumanInTheLoop 不会改空消息、LoopDetection 也不会改空消息， 所以 A 看到的 state["messages"][-1] 就是模型原始输出，判定条件成立。

但顺序不能随便放：如果放到 LoopDetectionMiddleware 之前（观察顺序更靠后）， 理论上 LoopDetection 有可能先给消息追加了软提醒文本或硬停文案——那时 A 的 _has_visible_content() 可能被「LoopDetection 追加的提示文本」骗成「有内容」， 从而错过真正的空响应。 所以 A 必须注册在 LoopDetection 之后（列表末尾），与 deer-flow「Safety 注册在 Loop 之后」的做法同构。

8.3 实测意外发现之一：jump_to 缺 hook_config 会被静默忽略

这是个坑，deer-flow 没提，但如果我们照抄代码时漏了装饰器，症状会非常隐蔽。
试验 D 一开始出现了「假阳性」：没加 @hook_config 也跑通了恢复。 深挖后发现是巧合——那次场景里 tools -> model 本来就是条件边， 删掉空消息后 LangGraph 自然又跑了一次 model，跟 jump_to 毫无关系。

于是重设计了试验 E（让「默认去向」不是 model），并直接探查运行时真值： 
_get_can_jump_to(NoHook(),    "after_model")  ->  []
_get_can_jump_to(WithHook(),  "after_model")  ->  ['model']
hasattr(NoHook.after_model, "__can_jump_to__")  ->  False

【实验 E】无 hook_config + jump_to="model"（默认去向应为 tools）
   工具是否真的执行了 = []   ← jump_to 被忽略，但也没有报错
   model 调用次数 = 2
源码机制（factory.py:1978-2002）：_add_middleware_edge 里 if can_jump_to: 为假时，走的是 graph.add_edge(name, default_destination) —— 静态边，根本不读 state["jump_to"]。 _get_can_jump_to 只在 sync 或 async 的 after_model 上带 __can_jump_to__ 属性时才返回非空， 否则静默返回 []（factory.py:525）。

对我们的要求：A 的 after_model 和 aafter_model 两个都要加 @hook_config(can_jump_to=["model"])。只给 sync 加、async 漏掉的话， 我们走 astream（异步路径）时就会命中这个静默失效 —— 表现为「空响应被删了但模型没重跑，直接结束」，比不修还糟。

8.4 实测意外发现之二：中间件 name 必须全局唯一

Spike 第一版直接 AssertionError: Please remove duplicate middleware instances. （factory.py:1080：if len({m.name for m in middleware}) != len(middleware)）。

对我们有两条实际约束：
  1. 测试/回归环境里不能塞两个同类探针中间件（比如两个 TerminalResponseMiddleware 实例做 A/B）—— 要动态建不同子类，或给实例改 name。
  2. 更实际的一条：deer-flow 的做法是同一实例跨 run 复用（用 BoundedDict 按 (thread_id, run_id) 存重试预算）。如果我们将来想「按用户/会话装两个守卫中间件」，会直接撞这个断言。 结论：保持单实例 + 内部按 key 分桶，别走「多实例」路线。

8.5 仍需在 67 环境复核的一点（不能省）

上表第 6 行 deepagents base stack 里的 TodoListMiddleware 也有 after_model。 按逆序它是最后被调用的（离 model 最远），但它的 _apply 会往 state 里写 todo 列表。 需要确认：它是否可能在本轮末尾改动 messages[-1]。
做法：在 67 上用真实 deepagents（含 base stack）跑一次「人为构造空响应」的用例， 打印每个中间件 after_model 入口处的 messages[-1] 快照，确认 A 拿到的仍是原始空消息。 这是 8.2 表格里唯一未能本地闭环的一项，其余均为实测结论。
