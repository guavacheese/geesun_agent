## 1. 现状诊断（基于真实代码）

### 1.1 思考 / 吐 token 状态（已实现过一轮修补，仍脆弱）
- 后端 `chat.py`：
  - 状态标志 `thinking_emitted` / `generating_emitted`（L579–582），`nonlocal` 已在 L621 补齐。
  - 每个 step 重置标记（L672–673）；首 reasoning → 发 `agent_status: thinking` + `reasoning`（L698–719）；首个答案 token → 发 `agent_status: generating`（L721–731、L729–731）。
  - 工具开始 → `agent_status: running_tool` + `tool`（L794）。
  - 收敛提示 → `agent_status: no_progress`（L1143）。
- 前端 `ChatArea.tsx`：
  - `agent_status` 事件直接 `setAgentStatus(event.status)`（L129）；`running_tool` 带 `tool` 名（L130）。
  - **已部分具备自纠**：token 到达 → `setAgentStatus("generating")`（L158，注释"即使后端误标 thinking，前端也能在此自纠"）；reasoning 到达 → `setAgentStatus("thinking")`（L184）。
  - 状态枚举 `AgentStatus = "idle" | "thinking" | "generating" | "running_tool"`（`types.ts:82`）。
- **仍脆弱点**：状态**主驱仍是后端 `agent_status` 枚举**。后端一旦漏发/错序（如新 step 重置后又未补发、或 reasoning 与 content 同 chunk 到达），前端只能等下一个事件才能纠正；`running_tool` 缺少稳定的 `tool_call_id` 配对，工具卡片无法幂等合并。

### 1.2 工具执行事件现状
- 后端**已发**结构化 `tool_result`（L872–888）：含 `id`(=tool_call_id)、`tool`、`success`、`error`、`result`。
- 后端**未发**配对的 `tool_call`（开始）事件——工具开始只用 `agent_status: running_tool`（无 `id` 配对）。
- 前端 `types.ts` 已定义 `"tool_call" | "tool_result"` 事件类型（L74–75），但 `tool_call` 事件当前无后端来源。

### 1.3 循环检测现状（P0，chat.py）
- 状态：`_last_tool_sig` / `_repeat_count` / `_files_in_window` / `_no_progress_injections`（L609–622）。
- 检测：工具成功但连续同一意图且无新交付物 → 注入收敛提示（L912–952），`recursion_limit=200`（L652）。
- 收敛耗尽（≥`no_progress_max_injections`）→ 直接终止并 yield `no_progress`（L946–952、L1133–1146）。
- **与 deer-flow 的差距**：当前是"单计数器 + 注入收敛"，没有 (a) 基于 tool_call 集合哈希的重复检测、(b) 基于同类工具频率的硬停、(c) "剥 tool_calls 自然收尾 + 显式 stop_reason"的优雅终止。

## 3. 总体方案

### 方案 A — 事件协议重构 + 派生式前端状态（去脆弱枚举）
**核心思想**：后端不再以 `agent_status` 枚举"指挥"前端显示什么，而是推送**不可丢失的事实事件**（reasoning delta、content delta、tool_call 开始、tool_result、file_generated）；前端从"消息内容 + 是否仍在流式"**反解**出当前应显示的形态（思考中 / 生成中 / 工具执行中）。`agent_status` 仅作为可选辅助信号。

**收益**：状态错乱从"前后端枚举必须严格对齐"降级为"前端自纠"，与 deer-flow 同构；后端漏发一个 status 不再导致 UI 卡在错误态。

### 方案 B — 循环检测增强（移植 deer-flow 双层 + 自然收尾）
在现有 P0 单计数器基础上，叠加：
1. **哈希层**：对每次 model call 的 tool_call 集合做哈希；相同集合 ≥3 次注入警告、≥5 次**剥掉 tool_calls 让 run 自然以最终答案收尾**（不抛异常），记 `stop_reason=loop_capped`。
2. **频率层**：同类工具累计调用次数：≥30 次注入警告、≥50 次硬停。
3. 警告在**所有 ToolMessage 就位后**（`wrap_model_call` 语义）注入，避免破坏 OpenAI/Anthropic 的 tool_call 配对。
4. 保留现有 P0 收敛注入作为第一道防线，双层互为补充。

## 4. 具体实施步骤（分阶段）

### Phase 0 — 配置项（低风险，先落地）
`src/core/config.py` 新增（可被 `.env` 覆盖）：
```python
loop_hash_warn = 3          # 相同 tool_call 集合告警阈值
loop_hash_cap = 5           # 相同集合剥 tool_calls 收尾阈值
loop_freq_warn = 30         # 同类工具累计告警阈值
loop_freq_cap = 50          # 同类工具硬停阈值
```
`AGENTS.md` 同步记录阈值含义。

### Phase 1 — 后端：补 `tool_call` 配对事件（中风险）
**文件**：`src/api/endpoints/chat.py`
- 在 L794 `running_tool` 处，额外 yield 一个结构化事件（复用现有 `tool_call_id` 取值，L799–877 附近已能取到 `tool_call_id`）：
```python
yield f"data: {json.dumps({
    'type': 'tool_call',
    'id': tool_call_id,
    'tool': tool_name,
    'args': <截断后的入参摘要>,
}, ensure_ascii=False)}\n\n"
```
- `tool_result`（L872–888）已带 `id`，保持不变；前端据此按 `id` 幂等合并卡片（pending→running→done/error）。
- 不动现有 `agent_status` 事件（兼容过渡期），但 Phase 2 后前端将优先以 `tool_call`/`tool_result` 推导 `running_tool` 形态。

### Phase 2 — 前端：派生式状态机（中风险，核心）
**文件**：`lib/types.ts`、`app/chat/components/ChatArea.tsx`
1. `types.ts`：保留 `AgentStatus` 枚举作为**派生结果**类型，新增 `ToolCallState = "pending" | "running" | "done" | "error"`；`ToolCallCard` 以 `id` 为 key 幂等更新。
2. `ChatArea.tsx`：改造 `agent_status` handler（L126–200）：
   - 删除"直接 `setAgentStatus(event.status)`"的硬赋值（L129）。
   - 改为**事件驱动派生**：
     - 收到 `reasoning` → 标记"当前 AI 消息处于思考态"（而非全局 thinking）。
     - 收到 `token`(content delta) → 标记"当前 AI 消息处于生成态"。
     - 收到 `tool_call` → 在工具卡片 map 里 upsert `{id, state:'running'}`；若当前无 AI 正文在生成，UI 显示"工具执行中"。
     - 收到 `tool_result` → 按 `id` 更新卡片 `{state: success?'done':'error'}`。
   - 全局 `agentStatus` 由"当前消息是否含未结 tool_call + 是否仍在流式"计算得出（对齐 deer-flow `getMessageGroups` 的 `isUnresolvedAssistantText` 思路），不再盲信后端枚举。
3. 保留 L118 的 prefill `thinking` 作为"首事件前占位"，收到首个 reasoning/token/tool_call 后由派生逻辑覆盖。

### Phase 3 — 后端：循环检测增强（方案 B）
**文件**：`src/api/endpoints/chat.py`（P0 区块 L912–952、L1133–1186）
- 新增模块级/闭包内 `_tool_call_hash` 计数器（哈希层）与 `_tool_freq` 计数器（频率层）。
- 在 model call 准备阶段（`wrap_model_call` 语义，即所有 ToolMessage 就位、下一轮 LLM 调用前）做检测：
  - 计算本次待发 tool_call 集合哈希；命中 `loop_hash_cap` → 不 raise，而是**剥离这些 tool_calls**（让 graph 以当前 context 直接生成最终答案），并 yield 一条 `agent_status: no_progress` + `stop_reason=loop_capped`。
  - 同类工具累计达 `loop_freq_cap` → 同上剥离 + 终止。
  - 阈值内（warn 级）→ yield 收敛提示（复用现有 L942 文案机制），不中断。
- **关键**：剥离 tool_calls 而非抛异常，避免 GraphRecursionError 整轮白等（对齐 deer-flow `stop_reason=loop_capped` 自然收尾）；保留现有 `_no_progress_injections` 收敛注入作为第一道。

### Phase 4 — 前端：渲染节流（低风险，可选增强）
- 若密集 token 出现卡顿，参照 deer-flow `useCoalescedStreamMessages`（80ms 合并 setState），在 `setMessages` 累加处加节流。
- 解析崩溃降级：streamdown/markdown 渲染失败时降级为纯文本（避免整页白屏）。
