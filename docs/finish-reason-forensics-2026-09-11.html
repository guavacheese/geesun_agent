四、认知纠正：D 项不需要 trace 后端

之前把 D（finish_reason 识别）的判断依据挂在「恢复 trace 导出」上是错的。 finish_reason 是运行时数据，就挂在 Agent 拿到的 AIMessage 上。 恢复 trace 只能让事后从 Phoenix/Langfuse 面板翻看，属于「可观测性加分」， 不是修复的必要条件。

证据一：我们代码里已经在读它了

// src/core/loop_detection.py:357-358
response_metadata = deepcopy(getattr(last_msg, "response_metadata", {}) or {})
if response_metadata.get("finish_reason") == "tool_calls":
    response_metadata["finish_reason"] = "stop"
既然 LoopDetectionMiddleware 能在 after_model 里读到它， A（TerminalResponseMiddleware）在同一个 hook 上必然也能读到。零额外成本。

证据二：deer-flow 也是这么做的

ModelLengthFinishReasonMiddleware._detect() 直接吃 AIMessage， 走的是 ModelLengthTerminationDetector 对 message 字段的检查， 完全不碰 OTel/Phoenix。它的 stop_reason 是写进 runtime.context 的。

证据三：生产已验证落点

第 2.2 节那条 Langfuse 样本（真实流式调用） "response_metadata": {"finish_reason": "tool_calls", ...} —— 落点确认无误。

项原定位修正后定位

4.1 三分支判定（我们独有的 reasoning 感知）

现在可以用 finish_reason + reasoning_content 做精准分流， 比 deer-flow 和 deepseek-harness 都细：
分支判据语义处置
① 正常 content 非空 正常收尾 放行
② thinking 截断 content 空 + reasoning_content 非空 + finish_reason == "length" 本次故障形态：思考吃光 65536 输出预算被硬截断 删空消息 + jump_to="model" 重试 1 次； 重试提示要明确告知「上轮思考超长被截断，请直接给结论」
③ 思考完没说 content 空 + reasoning_content 非空 + finish_reason == "stop" 想完了但没输出正文（模型行为问题） 同 ② 的重试，但提示语不同（「你已有结论，请输出正文」）
④ 彻底空 content 空 + reasoning_content 空 完全没吐东西 重试 1 次；仍空则写降级文案
为什么我们能做四分支、两个参考仓只能做两分支：
  • deer-flow 的 ModelLengthFinishReasonMiddleware if not _has_visible_content(last): return None → ②③④ 它全部跳过；
  • deepseek-harness 判空靠 order.length === 0，而 reasoning block 计入 order → ②③ 它判不出来；
  • 我们因 ReasoningChatOpenAI（model.py:251-282）把 thinking 分离进 additional_kwargs["reasoning_content"]，content 与 thinking 天然可分辨 → 四分支全可做。

7.2 关键实测：request.override() 注入不会进 state

这纠正了我上一版的错误推断。原以为「注入的 HumanMessage 会被 _persist_session 落库」， 但实测证明：通过 request.override(messages=...) 注入的消息只对本轮模型调用可见， 不会写回 agent state，因此不会进 checkpoint、不会被持久化。
脚本：.workbuddy/spikes/inject_state_spike.py，用真实 create_agent + 脚本化模型对照两种注入方式： 
### A_override —— wrap_model_call + request.override(messages=[...加 HumanMessage...])
模型实际看到：  ['HumanMessage:hi', 'HumanMessage:[[INJECTED-REMINDER]]']  ← 模型能看到提示
最终 state：    HumanMessage 'hi' / AIMessage 'reply1'
                >>> 注入消息未进入 state ✓ 不污染历史

### B_state —— after_model 返回 {"messages": [HumanMessage(...)]}
模型实际看到：  ['HumanMessage:hi']                                     ← 本轮模型反而没看到
最终 state：    HumanMessage 'hi' / AIMessage 'reply1' / HumanMessage '[[INJECTED-REMINDER]]'
                >>> 注入消息进入了 state ✗ 会被落库污染历史
两条结论：
  1. request.override() 是「只读注入」 —— 符合我们「重试对用户不可见」的需求， 且不需要 hide_from_ui 配合。
  2. 我们现有的 loop_warning 没有污染历史 —— 它正是走 loop_detection.py:410-412 的 request.override() 路径。 之前担心的「既有同类问题」并不存在。

model -> TerminalResponseMiddleware.after_model
      ├─ jump_to="model"  ────────────────────→ model      ← 命中空响应时走这条

                            ├─→ model
                            └─→ tools ──→ model
实测计数：模型被调用 2 次，而 LoopDetection 只被调用 1 次。

11.5 本机构建踩到的坑（ghcr.io + BuildKit）

症状：构建在 第一步就失败，报 failed to fetch anonymous token: Get "https://ghcr.io/token?...": EOF， 且重试同样失败（稳定复现，不是瞬时抖动）。
排查（每步都有对照实验）：
  • 容器内 urllib.request.urlopen(ghcr.io/token…) → HTTP 200 且拿到 token（网络与 TLS 都正常）
  • BuildKit 构建 FROM alpine:3.20 → 成功（Docker Hub 走 registry-mirrors）
  • docker pull ghcr.io/astral-sh/uv:python3.13-bookworm → 成功，8 层全 Already exists
⇒ 根因：BuildKit 的 registry metadata resolver 与 dockerd 的经典 puller 走了不同的出网路径； 镜像其实早就在本地（上次构建拉的），但 BuildKit 仍要联网重新解析 tag。
修复（一行，无需改 Dockerfile、无需重启 Docker Desktop）： 
docker pull ghcr.io/astral-sh/uv:python3.13-bookworm   # 让 tag 在本地可解析
bash build_agent_only.sh 1.0.8                       # 此后 #3 load metadata = DONE 0.0s
修复后依赖层全部 CACHED，构建从 5–15 分钟降到 2 分 15 秒（只重跑最后两层）。 已写入 geesun-release-prep 陷阱 8。
