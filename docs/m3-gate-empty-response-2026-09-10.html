三、根因分析：两层，一层是模型异常，一层是门控放大

第 1 层（直接原因）：模型返回空响应，且代码全程无兜底

最后一次调用耗时 336 秒后返回 content 空 + tool_calls 空。全仓 grep 确认： 不存在任何针对「空响应 / 零 tool_calls」的检测与重试逻辑（grep 空响应|empty_retry 零命中）。

空 AIMessage 进入 deepagents 的 agent loop 后，因为没有 tool_calls，循环直接判定「结束」， 连一次纠偏机会都没有 —— 这与 model.py:517 注释里记录过的历史事故是同一类失效模式：

# effective_max 被 floor 到 1 → max_tokens=1 → 模型几乎零产出（截断在"用户"后无输出）
# → 无 AIMessage → agent 永不结束 → 反复空转。现改为超预算时砍输入（优先图片块）、
# 保底 1024 输出空间，杜绝 floor=1 死循环（见 docs/context-window-fix-draft.md v2）。

说明这一失效模式此前已被识别过一次，但只修了「floor=1」这条触发路径，没有加通用兜底。

第 2 层（放大原因）：auto_continue=false 让完成门退化成「一次空输出 = 终局」

完成门的判定与处置分支在 chat.py:1358-1373：

if (_completion_retries >= settings.sandbox_completion_gate_max_retries
        or not settings.sandbox_completion_gate_auto_continue):
    _completion_blocked = True
    logger.warning("[M3] 完成门拦截（本轮零产出）: ... retries=%d", ...)
    yield completion_blocked  →  break

线上配置（/opt/geesun/deploy/.env:78 与容器内 env 双确认）：

配置键线上值含义
sandbox_completion_gate_enabledtrue完成门开启
sandbox_completion_gate_auto_continuefalse零产出时不注入继续轮 → 立即判失败
sandbox_completion_gate_max_retries2本可重试 2 轮（但被上一行短路，形同虚设）

因为 not auto_continue 恒为真，判定在第 0 次就命中拦截 —— 这正是日志里 retries=0 的含义：一次继续轮都没试过。 max_retries=2 与「注入 SystemMessage 自动继续」这段能力被配置直接短路成了死代码。

因果合并：模型的一次瞬时异常（336s 空响应）＋ 门控的零自愈配置 ＝ 用户看到终局失败。 两者缺一不会产生这个结果。若 auto_continue=true，本例极可能在第 1 轮继续轮自愈（重放该次调用即大概率正常返回）。

可疑点深挖：336 秒这个数字本身很可疑

时长与输出上限的数值巧合值得警惕：

336 s  ×  ≈195 tok/s（Qwen3.6-35B-A3B 合理吞吐）  ≈  65.5k tokens   ≈   model_max_tokens = 65536

假设 A（可能性最高）：thinking 吃光输出预算，被 finish_reason=length 截断在思考段内。

  • 本项目用 --reasoning-parser qwen3，思考走 delta.reasoning、正文走 delta.content，二者完全分离 （见 model.py:251-282 的 ReasoningChatOpenAI 注释与实测：680 个 reasoning chunk / 2045 字符 vs 46 个 content chunk）。
  • 若模型在 think 段内跑满 max_tokens，parser 始终没遇到思考闭合标签 → 全部生成 token 落在 reasoning 字段 → content 恒为空；同时思考未结束，自然也不会发 tool_calls。
  • 这完美解释「336 秒长思考 + 最终 content 空 + tool_calls 空」三者同时出现。

假设 B：模型自身空转/异常。可能性低于 A，但同样无法用现有日志证伪。

无法定论的原因（重要）：定论需要该次调用的 finish_reason / completion_tokens / reasoning 全文。 但 ea303fe（2026-09-09）已把 src/core/tracing.py 的 Phoenix / Langfuse / metrics 三处 exporter 全部注释 —— 实测查询 Phoenix spans 表在 17:33~17:41 窗口 返回 0 行，trace 侧证据链已断。这就是「排查时拿不到模型侧判决」的直接原因。

四、为什么说不合理（用户判断成立）

  1. 归因文案是错的、且会误导排障。提示让用户「检查是否遗漏 download_from_sandbox / write_file」， 但本例 agent 连一次 tool_call 都没发出，压根没走到下载环节。文案把「模型异常」伪装成「流程漏步」， 会把排障方向带偏（chat.py:1369-1370）。
  2. 零自愈 + 终局判定。一次瞬时异常即判死，max_retries=2 形同虚设，用户需手工重发， 且重发后会话历史里已留下「失败」标记。
  3. retries=0 说明系统连「确认一次」都没有做，与完成门「不信任模型自陈、系统校验」的设计意图相悖 —— 它校验了产出，却没校验「模型是否真的回答了」。
  4. 偶发但被放大。24h 全量日志 grep 显示这是唯一一次完成门拦截，说明不是高频缺陷； 正因为低频，它在生产里会以「偶发、无法复现、用户困惑」的形态反复出现，成本高于修一次。
